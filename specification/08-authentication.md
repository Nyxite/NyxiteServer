# 08 — Authentication, Keys & Authorization

> **E2EE.** Login (**Nyxite-native account auth** by default — password + a required second factor, or passkeys) authenticates the *account*; a separate **device-key / identity-keypair** layer governs *decryption*. The two are deliberately distinct: authenticating does not hand the server any content key. Native auth is the baseline; Keycloak/OIDC is a pluggable **enterprise** IdP. (Canonical model: [SPECIFICATION §10](https://github.com/Nyxite/Nyxite) / [OPEN-DECISIONS #9](https://github.com/Nyxite/Nyxite).) Concrete flows are **[P]**.

## 8.1 Identity model (native by default; pluggable IdP seam)

- **Nyxite-native, server-owned authentication is the default for all tiers.** The server keeps a real account store, not a thin IdP projection: per user a **password verifier** (Argon2id over a peppered HMAC pre-hash — [§8.1(a)](#81-identity-model-native-by-default-pluggable-idp-seam)), a **verified email address**, the enrolled password second factors (**TOTP secret**, **emailed codes**, **backup codes**), and zero or more **WebAuthn/passkey credentials** ([02](02-domain-model.md), [03](03-data-model.md)).
- **Two co-equal primary methods** from day one:
  - **(a) Password + required second factor** — the password verifier is **Argon2id over an HMAC-SHA256(password, pepper) pre-hash** (pinned Argon2id params m=64 MiB, t=3, p=1 — [07](07-encryption.md)); a second factor is **mandatory**, not optional. The server sees the password only **transiently** over TLS at login and stores only the verifier, never the password. The second factor is one of:
    - **TOTP** (RFC 6238). Every code is accepted once: `users.totp_last_step` records the time step of the last accepted code, and a code is only accepted for a later step (RFC 6238 §5.2). Without this a code seen over a shoulder or in a log would sign in again for up to 90 s.
    - **Emailed code.** An 8-digit code sent to the verified account address. It is the weakest factor, because the mailbox is also the password-reset channel and whoever controls it would hold both factors. An account that enables email codes therefore **cannot reset its password by email** (`/auth/password/forgot` sends nothing for it). Email codes exist for people without an authenticator app or passkey. NIST SP 800-63B does not accept email as an out-of-band authenticator, and the reset exclusion is what keeps the two factors independent.
    - **Backup code.** One of `NYXITE__Auth__BackupCodeCount` single-use codes (10 Crockford base32 characters, `XXXXX-XXXXX`), shown once and stored as keyed hashes ([03](03-data-model.md) `backup_codes`). They replace a lost factor and are never a factor on their own, so an account needs TOTP, email codes or a passkey before it can create them. Backup codes were chosen over security questions, which were also considered: answers can be guessed or researched, NIST SP 800-63B forbids knowledge-based authentication, and the server would have to store personal facts about the user.
    - **Pepper (defense-in-depth):** the **pepper** is a **versioned, rotatable server secret held OUTSIDE Postgres** — a deploy secret `PASSWORD_PEPPER` alongside the DB credentials ([14](14-deployment-and-config.md)) — so a **DB-only leak yields uncrackable verifiers** (the attacker lacks the pepper). The per-hash Argon2id **salt is unchanged** (already inside each verifier). Rotation **re-peppers lazily at each user's next successful login** (the HMAC pre-hash cannot be recomputed without the plaintext, transiently available only then); the verifier records its pepper version.
    - **Boundaries:** the pepper is **account-auth defense-in-depth only** — the login password still **NEVER** feeds any content-key derivation (see the load-bearing rule below), the pepper is symmetric so it has **no PQC dimension**, and it is **NOT** applied to the recovery-phrase Argon2id path (that key is user-held and server-blind — a pepper there would break offline self-recovery, [07 §7.8](07-encryption.md)).
  - **(b) Passkeys (WebAuthn)** — phishing-resistant public-key credentials, **sufficient on their own** (no separate TOTP needed). The server stores only the credential's **public** key + signature counter.
- **Load-bearing rule: the login password (or passkey) NEVER feeds any content-key derivation.** Account auth and content access are independent secrets — content keys come only from the identity / device / recovery-phrase path ([07 §7.8](07-encryption.md)). So an account/password compromise yields **no content**.
- **Property restatement:** "no passwords on the server" → **"no content-derivable secrets on the server."** Argon2id password verifiers and passkey public credentials unlock an **API token, never a key**.
- **Pluggable IdP seam — IdP-agnostic API.** Identity providers plug in behind **one internal token**; the rest of the API never sees which IdP authenticated the user. Native auth is one provider; **(enterprise) Keycloak-OIDC** is another. Both resolve to the **same server-issued token** ([§8.2](#82-token-model-p)).
- **Keycloak / OAuth-OIDC SSO is an enterprise-tier option** (optional `enterprise` deploy profile — [14](14-deployment-and-config.md)), **not the default and not load-bearing**. When enabled, the server validates the OIDC token, links/provisions a native `users` row via `external_idp`/`external_idp_sub`, and **mints its own internal token** so downstream code is unchanged. **Licensed enterprise feature (L-3):** the OIDC path is gated behind entitlement flag `ent.sso` ([16 §16.5](16-licensing-and-entitlement.md)) — in **community mode** it is disabled and only native password+TOTP / passkeys are offered; a lapsed license degrades it (existing sessions frozen, no new OIDC logins).
- **Enterprise OIDC flow (detail).** The server is a **confidential** OIDC client of Keycloak (`ClientId`/`ClientSecret`, endpoints discovered from `<Authority>/.well-known/openid-configuration`, JWKS cached and refreshed on an unknown `kid`).
  1. `GET /auth/oidc/authorize?client=desktop|android|web&redirectUri=` — `redirectUri` must be on the allowlist `NYXITE__Auth__Enterprise__RedirectUris` (app deep link such as `nyxite://oidc` or the web origin), else `400`. The server creates `state`, `nonce` and a PKCE `code_verifier` (S256), stores them as one `ephemeral_tokens` row of kind `oidc_state` (10 min), and redirects to the IdP with scope `openid email profile`.
  2. `GET /auth/oidc/callback?code=&state=` — consumes `state` (single-use), exchanges `code` with the client secret and `code_verifier`, and validates the ID token: signature via JWKS, `iss` = Authority, `aud` = ClientId, `exp`, `nonce`. It maps `sub` to `users.external_idp_sub`. An unknown `sub` provisions a new user. **An existing native account with the same email is never linked automatically**, because email equality is not proof of control; the user links it from a signed-in native session instead. Then it creates a session (`auth_method = 'oidc'`; the IdP is responsible for MFA) and redirects to `redirectUri` with a one-time `handoff` code (kind `oidc_handoff`, single-use, 60 s).
  3. `POST /auth/oidc/token { handoff }` → `{ accessToken, refreshToken }`. Tokens are never put in a redirect URL, where they would land in browser history and logs.
- **Account recovery ≠ content recovery.** Forgot-password / email reset restores **login only**; content still requires the **recovery phrase** or an **enrolled device** ([07 §7.8](07-encryption.md)). Email/account compromise yields no content. An account that uses emailed codes as its second factor cannot reset its password by email (see (a) above).
- **Email verification.** Registration emails an 8-digit code, confirmed with `POST /auth/email/verify`. Until then the session can only verify, ask for a new code, refresh and log out, and every factor enrollment answers `403 email_unverified`. An account still unverified after `NYXITE__Auth__UnverifiedAccountLifetime` (default 24 h) is purged, at the next registration or login with that address and by a background job every `NYXITE__Auth__UnverifiedAccountSweepInterval`, and its address is free again. Without verification, whoever registered an address first owned it: the real owner got `409`, and a squatter who enrolled their own second factor kept the account. The purge needs no admin action and deletes nothing of value, because an unverified account never had a factor, keys or content. Verification before enrollment was chosen over verification before full login, so an unverified account never becomes usable at all. A server without a mail relay cannot verify anyone, so `NYXITE__Email__Host` and `__From` are required at startup ([14](14-deployment-and-config.md)).

### Native auth endpoints **[P]**

All under `/api/v1/auth` (unauthenticated except where noted); they issue/refresh the server's own tokens ([04](04-rest-api.md)). When the `enterprise` profile is on, an additional `GET /auth/oidc/*` (authorize/callback) flow resolves to the same token.

| Method | Path | Purpose |
|--------|------|---------|
| `POST` | `/auth/register` | Create a native account: `{ email, displayName, password, clientKind }` → user row with a peppered Argon2id verifier ([§8.1(a)](#81-identity-model-native-by-default-pluggable-idp-seam)) and an emailed verification code. Email verification and then factor enrollment are required before first full login |
| `POST` | `/auth/email/verify` | (auth'd, limited session allowed) Confirm the email `{ code }` |
| `POST` | `/auth/email/verify/resend` | (auth'd, limited session allowed) Email a new verification code, replacing the old one |
| `POST` | `/auth/login` | Password login: `{ email, password, clientKind }` → `{ challenge: "second_factor_required", mfaToken, methods }` with `methods` ⊆ `totp`, `email`, `backup_code` (password-only never yields a full token; a second factor is mandatory). An account with no second factor yet gets `{ challenge: "enrollment_required", accessToken, refreshToken, accessTokenExpiresAt }` of an enrollment-limited session instead, so a lost registration session cannot lock it out. A passkey-only account without backup codes gets `401` |
| `POST` | `/auth/login/totp` | Complete login: `{ mfaToken, totpCode }` → `{ accessToken, refreshToken }` |
| `POST` | `/auth/login/email/send` | Email a sign-in code for `{ mfaToken }` (accounts with email codes only); sending again replaces it |
| `POST` | `/auth/login/email` | Complete login: `{ mfaToken, code }` → `{ accessToken, refreshToken }` |
| `POST` | `/auth/login/backup-code` | Complete login: `{ mfaToken, code }` → `{ accessToken, refreshToken }`; the code is spent |
| `POST` | `/auth/totp/enroll` | (auth'd) Begin TOTP enrollment `{ stepUpToken? }` → `{ secret, otpauthUri }`; secret stored only after verify |
| `POST` | `/auth/totp/verify` | (auth'd) Confirm enrollment `{ totpCode }` → activates the second factor |
| `POST` | `/auth/email-otp/enroll` | (auth'd) Begin enabling email codes `{ stepUpToken? }`: emails a confirmation code |
| `POST` | `/auth/email-otp/verify` | (auth'd) Confirm `{ code }` → email codes become a second factor |
| `POST` | `/auth/backup-codes` | (full session) `{ stepUpToken }` → `{ codes }`, a new set that replaces the old one, shown once |
| `POST` | `/auth/step-up` | (full session) `{ method, code?, credential? }` with `method` ∈ `totp`, `email`, `backup_code`, `passkey` → `{ stepUpToken, expiresAt }` ([§8.2](#82-token-model-p)) |
| `POST` | `/auth/step-up/email` | (full session) Email a step-up code (accounts with email codes only) |
| `POST` | `/auth/step-up/passkey/options` | (full session) WebAuthn request options limited to the caller's passkeys |
| `POST` | `/auth/webauthn/register/options` | (auth'd) Begin passkey registration `{ stepUpToken? }` → WebAuthn creation options (challenge) |
| `POST` | `/auth/webauthn/register` | (auth'd) Finish registration: attestation response → stores a `webauthn_credentials` row |
| `POST` | `/auth/webauthn/assert/options` | Begin passkey login `{ email? }` → WebAuthn request options (challenge). The email is ignored and `allowCredentials` stays empty, because passkeys are registered as discoverable and a per-email answer would reveal which accounts have passkeys |
| `POST` | `/auth/webauthn/assert` | Finish passkey login: `{ credential, clientKind }` → `{ accessToken, refreshToken }` (sufficient alone) |
| `GET` | `/auth/oidc/authorize`, `/auth/oidc/callback`; `POST /auth/oidc/token` | **Enterprise profile only** (`ent.sso`): OIDC login, detail in [§8.1](#81-identity-model-native-by-default-pluggable-idp-seam) |
| `POST` | `/auth/refresh` | Exchange a valid refresh token → a new `{ accessToken, refreshToken }` |
| `POST` | `/auth/logout` | Revoke the presented refresh token (and current session) |
| `POST` | `/auth/password/forgot` | Start email-based reset → emailed token (**restores login only**, never content) |
| `POST` | `/auth/password/reset` | Complete reset `{ resetToken, newPassword }` → new peppered Argon2id verifier (current pepper version) |

- **Factor enrollment rules.** Enrolling (`/auth/totp/enroll`, `/auth/email-otp/enroll`, `/auth/webauthn/register/options`) needs a verified email. An account without any factor may enroll its first one from any session, including the limited one. Once a factor exists, adding or replacing one needs a full session **and** a step-up token on the request that starts the change ([§8.2](#82-token-model-p)), and completing it revokes the account's other sessions (`credential_change`, [§8.7](#87-sessions--logout)).
- **Account-wide code cap.** Wrong second-factor codes (login, step-up, email verification) are counted per account over `NYXITE__Auth__SecondFactorFailureWindow`. At `NYXITE__Auth__SecondFactorFailureLimit` further attempts answer `429 rate_limited` with `Retry-After` until the oldest counted failure leaves the window. The per-`mfaToken` cap alone did not bound guessing, because whoever has the password can open new `mfaToken`s. The count is read from `audit_log`, where every failure is already recorded, so no extra state is kept. The cap can lock out the owner for the window, but only someone who already has the password can trigger it, and passkey login is not affected.
- **Blocked accounts.** A `blocked` account ([12 §12.6](12-administration.md)) gets no `web` session: every sign-in path ends in the session service, which answers `403 account_blocked` and audits `auth.login_failed` with reason `account_blocked`. A web session that existed before the block is revoked (`user_blocked`) at its next refresh. Desktop and Android sessions continue, because a blocked account keeps download access.
- **`clientKind`** (`desktop`/`android`/`web`/`admin`) is sent in the body of every call that starts a session and is stored as `sessions.client_kind` ([03](03-data-model.md)). The password step carries it to `/auth/login/totp` inside the `mfaToken` row. A body field was chosen over a custom header or the User-Agent because it is explicit, validated against the enum and visible in the contract.
- **TOTP secret at rest.** `users.totp_secret_enc` is AES-256-GCM under `HKDF-SHA256(pepper_v, info = "nyxite-totp-secret-v1")`, laid out as `pepper_version(u32) ‖ nonce(12) ‖ ciphertext ‖ tag(16)` with AAD `"NYXTOTP1" ‖ user_id`. Deriving the key from the pepper needs no further deploy secret and keeps it outside Postgres. The secret is re-encrypted under the current pepper at the next password login, together with the lazy re-pepper. A separate TOTP key was rejected as one more secret to deploy and rotate for no added protection.
- **Passkey challenges** are single-use `ephemeral_tokens` rows of kind `webauthn_challenge` ([03 §3.2](03-data-model.md)). The WebAuthn relying party is configured by `NYXITE__Auth__WebAuthn__*` ([14](14-deployment-and-config.md)). Until it is set, the passkey endpoints answer `503 unavailable`.
- **Account auth ≠ content access.** A successful login (any method) yields an access token for the API but **no content key**. Content keys come from the user's **identity private key**, held on devices ([§8.3](#83-device--identity-keys-the-e2ee-layer)).

## 8.2 Token model **[P]**

- **The Nyxite server issues its own access + refresh tokens.** Native auth and (enterprise) Keycloak-OIDC are **pluggable identity providers** that both resolve to **one internal token**; the rest of the API is IdP-agnostic and never sees which IdP was used.
- **Access token format = JWT, `HS256` (HMAC-SHA256)** ([RFC 9068](https://www.rfc-editor.org/rfc/rfc9068) profile), signed with the server's own **token-signing key** ([14](14-deployment-and-config.md)). A symmetric MAC is enough because **only the server that issued a token ever verifies it**; there is no third-party verifier that would need a public key. That also keeps it quantum-safe without a hybrid signature, which would add ~3.4 KB to every request header for no gain. Opaque tokens with a DB lookup per request were rejected for the per-call round-trip (revocation is handled by the session, [§8.7](#87-sessions--logout)).
  - **Header:** `{ "alg": "HS256", "typ": "at+jwt", "kid": "<key version>" }`. The verifier **accepts only `HS256` and only `typ: at+jwt`**, which blocks algorithm-confusion and token-type confusion. `kid` names the key version, so `NYXITE__Auth__TokenSigningKey` can hold the current and the previous key during a rollover.
  - **Claims:** `iss` (instance base URL), `aud` (`NYXITE__Auth__Audience`), `sub` (`users.id`), `sid` (`sessions.id`, [03](03-data-model.md)), `role` (`user`/`admin`), `amr`, `iat`, `exp` (`iat` + ~5 min), `jti`.
  - **`amr`** ([RFC 8176](https://www.rfc-editor.org/rfc/rfc8176)) says how the session authenticated: `["pwd","otp","mfa"]` after password + TOTP, emailed code or backup code (`sessions.auth_method` tells them apart), `["hwk","user","mfa"]` after a passkey, `["fed","mfa"]` after enterprise OIDC, and only `["pwd"]` for an enrollment-limited session. Every endpoint except email verification, factor enrollment, refresh and logout requires `mfa`, otherwise it answers `403 2fa_required`. A standard claim was chosen over a custom `scope` so the meaning is defined outside Nyxite. **No email or display name** — a token travels in headers and logs, so it carries only what authorization needs; clients read profile data from `GET /me`.
  - **Guest share-session token:** same format with `typ: "nyx-guest+jwt"` and claims `share_id`, `perm` (`read`/`write`), `iat`, `exp` (15 min), `jti`. The distinct `typ` means a guest token is never accepted where an access token is expected, and vice versa.
  - **Refresh tokens and socket tickets are not JWTs** but opaque random values stored as hashes ([03 §3.2](03-data-model.md)), because they must be single-use.
- **Enterprise profile:** the OIDC login path uses Authorization Code + PKCE against Keycloak; the server validates that token against Keycloak **JWKS** (`iss`, `aud`, `exp`, signature), maps the external `sub` to a native `users` row, and then **issues its own internal token** — downstream is identical to native login.
- **Token lifetimes [P]:** access token **~5 min**; refresh token rotated on use; relay **socket ticket** single-use, **60s** TTL; guest **share-session token 15 min**, renewable while the share is valid (revocation effective within one renewal cycle). **Storage:** `mfaToken` and the socket ticket are hashed, single-use rows in `ephemeral_tokens`; the `pairingCode` is a hashed column on the pending `devices` row; the guest share-session token is **stateless** (signed, re-checked against `shares` on renewal) and not stored ([03 §3.2](03-data-model.md)).
- **2FA step-up** — sensitive **account/admin** actions require a recent second factor; if the step-up is missing the server returns **`403 2fa_required`**. (There is no content break-glass to gate — content is unreadable to the server regardless.)
  - **Mechanism.** `POST /auth/step-up` proves an existing factor again (TOTP, emailed code, backup code or a passkey assertion against a challenge from `/auth/step-up/passkey/options`) and returns a random **step-up token**: single-use, bound to the user and the session, valid for `NYXITE__Auth__StepUpLifetime` (default 5 min), stored hashed as `ephemeral_tokens` kind `step_up` ([03](03-data-model.md)). The request that starts the sensitive action carries it as `stepUpToken` and consumes it. A missing, used, expired or foreign token answers `403 2fa_required`, and a wrong factor answers the same and is audited as `auth.step_up_failed`.
  - **Why proof per action rather than a recent-factor window.** A window ("a factor within the last x minutes") lets every access token of a fresh session through, including one stolen right after login. A step-up token needs the factor itself, so a stolen access token alone can never add a passkey or replace TOTP. The cost is one extra prompt per change.
  - **Email as step-up proof** is accepted only for accounts that use email codes, so email never becomes a way around TOTP for an account that did not choose it.
  - **Current scope:** every factor change (TOTP, email codes, passkey, backup codes). Admin actions and password change join when they are built.

## 8.3 Device & identity keys (the E2EE layer)

- On first sign-in a client **enrolls a device** and ensures the user has an **identity keypair** (hybrid **X25519 + ML-KEM-768** for wrapping, **Ed25519 + ML-DSA-65** for signing — [07 §7.3](07-encryption.md)). The **public** keys go to the server directory (`user_keys`); private keys stay on the device ([03](03-data-model.md), [07](07-encryption.md)).
- **Enrolling a device:** `POST /devices { label, pubkey }` → `{ deviceId, status:"pending", pairingCode, qrPayload }`. An enrolled device approves it via `POST /devices/{id}/approve { pairingCode, wrappedIdentityKey }` — the approving device obtains `pairingCode` from the scanned QR or the typed numeric code, and the **server verifies it** (hash match, unexpired, under the attempt cap) before accepting the identity bundle **HPKE-sealed** to the pending device's `pubkey` into `pending_key_blob`. The approving device also checks that the pending device's `pubkey` returned by the server matches the **public-key fingerprint carried in the QR payload** (`qrPayload = { deviceId, pairingCode, pubkeyFingerprint = SHA-256(pubkey) }`); for the typed-code fallback the approving device shows the first 8 hex characters of that fingerprint, and the user compares them with the new device's screen. Without it the server could substitute its own `pubkey` and receive the identity bundle. The pairing-code check is server-side because an approval without proof of physical proximity would let anyone holding a session approve an attacker's pending device. The new device then calls `GET /devices/me/enrollment` to fetch `{ wrappedIdentityKey }` **once** (single-use; the server clears the blob and marks the device `active`). Alternatively the device recovers the identity private key via **recovery-phrase** unwrap ([07 §7.8](07-encryption.md)).
- **Activation without an approval.** The first device of an account and a device restored from the recovery phrase have no enrolled device to approve them. Such a device proves possession of the identity private key by signing its own enrollment (`POST /devices/{id}/activate`, message in [04](04-rest-api.md)), and the server verifies that signature against the live directory key before marking the device `active`. Key rotation, device approval and recovery-blob replacement require a session bound to an active device, so an attacker with the password and a second factor but no device cannot replace the owner's keys or recovery path.
- **Recovery key** (user-held, shown once) derives an Argon2id key that unwraps the **AES-256-GCM** recovery blob (`recovery_blobs`); it is the **only** way back in if all devices are lost ([07 §7.8](07-encryption.md)). No server/admin escrow.

## 8.4 WebSocket / relay upgrade auth

- The relay socket ([05](05-realtime-collaboration.md)) authenticates the upgrade with a **short-lived token** — a user bearer, a **single-use socket ticket (60s TTL)** minted from it, or a guest **share-session token (15 min)** ([§8.2](#82-token-model-p)).
- The share token authorizes **relay access** only; the **decryption key** comes from the link's URL fragment ([09 §9.4](09-sharing-and-acl.md)), never the server.

## 8.5 Authorization model

Two independent gates:

1. **Server ACL** — can the principal reach the ciphertext / join the relay? (owner / grantee / link / admin-structure-only).
2. **Crypto** — can they *decrypt*? Requires the right wrapped or fragment file key. The server cannot influence this.

Resource-action policies **[P]**:

| Policy | Grants (server ACL) |
|--------|---------------------|
| `resource:read-ciphertext` | Owner, grantee (read/write), guest via link, **admin: no** |
| `resource:write` | Owner, grantee `write`, guest via write link |
| `resource:share` | Owner |
| `admin:*` | Admin role (structure/usage/audit only) |

> Note there is **no `resource:read-content`** — reading content is a purely client-side capability gated by key possession, not a server permission.

## 8.6 Admin distinction

The `admin` role lives on the native account (`users.role`); when the enterprise IdP is enabled, a Keycloak claim may be mapped onto it. An admin manages instance/users and sees **structure/usage/audit**. Admins **cannot read content** — no key exists for them, and there is **no break-glass** ([12](12-administration.md)). This is stronger than the master spec's "audited break-glass": the capability simply does not exist.

## 8.7 Sessions & logout

- Stateless bearer auth on the server's own access token; logout/refresh are handled by the native `/auth/refresh` and `/auth/logout` endpoints ([§8.1](#81-identity-model-native-by-default-pluggable-idp-seam)) — refresh tokens rotate on use and can be revoked. Device keys persist locally until the device is revoked.
- **Server-side state.** Each sign-in creates a `sessions` row; its refresh tokens are opaque, stored only as SHA-256 hashes in `refresh_tokens`, single-use, and chained by `parent_id`. Re-presenting a used token revokes the whole session (reuse detection). Logout, admin force-logout, device revocation, blocking a user (a web session at its next refresh), and a credential change revoke the session. A credential change is a password change or adding or replacing any second factor (TOTP, email codes, passkey, backup codes) on an account that already had one. Adding counts as well as replacing, because a new passkey or code signs in on its own, so whoever added it must not keep sessions the owner does not know about. The session that made the change stays. The first factor of a new account revokes nothing, because there was nothing to protect yet. the stateless access token then expires within ~5 min. Schema and rationale: [03 §3.2](03-data-model.md); lifetimes: [14](14-deployment-and-config.md).
- Guest relay sessions use a **15-minute** share-session token, renewable while the share is valid; revoking the share cuts off new sessions instantly and live ones within one renewal cycle ([09 §9.6](09-sharing-and-acl.md)).

## 8.8 Auditing

Auth events, device enrollment/revocation, key publication/rotation, recovery use, share issuance — all audited ([12](12-administration.md)); keys and content never logged.

## 8.9 Rate limiting

Auth-adjacent endpoints, key-directory lookups, device enrollment, and share/link access are rate-limited ([13](13-security.md)).

- **Auth bucket.** Every endpoint that checks a password or a code, or sends one, shares a fixed window per client IP (`NYXITE__RateLimiting__Auth__PermitLimit` per `__Window`, default 10 per minute): register, login and its second-factor steps, passkey assertion, email verification, email-code enrollment and step-up. Over the limit the server answers `429 rate_limited` with `Retry-After`. Refresh is not in the bucket, because it presents a 256-bit token with nothing to guess.
- **Client IP.** The IP comes from `X-Forwarded-For` only when the request arrives from a configured proxy hop (`NYXITE__Network__KnownProxies` / `__KnownNetworks`, [14 §14.6](14-deployment-and-config.md)). Otherwise the header is ignored, because a client could set it to a fresh value for every request and escape the limit.
- **Per account.** The account-wide code cap ([§8.1](#81-identity-model-native-by-default-pluggable-idp-seam)) bounds guessing by someone who rotates IPs.
